# リアルタイム文字起こしと本人による回答の確認

音声入力中に文字起こしを表示し、候補者が認識結果を確認・訂正してから回答として確定する。AI面接でも、候補者側のAI利用や代行を完全には見抜けない。カメラ、視線、回答内容のいずれか一つで本人回答を保証する設計にはしない。

## 現在のデモ

質問画面の「文字起こしデモを開始」で、選んだ職種の架空回答を少しずつ表示する。認識途中の表示、一時停止、再開、途中での終了、最初からの再生を試せる。「この文字起こしを回答に使う」を押すまで、入力済みの回答を上書きしない。反映後は通常の回答欄で訂正できる。質問・招待を切り替えると再生を停止する。

ブラウザのマイク、カメラ、SpeechRecognition、音声ファイル、外部APIは使用しない。タイマーで架空テキストを表示するUIデモであり、実際の認識品質・遅延・通信切断の試験ではない。手入力と「ダミー回答を入力」も利用できる。

## 本番の文字起こし

1. 開始前に音声の送信先・利用目的・保存の有無と期間・中止方法を説明し、許可を得る。開始操作後にだけマイクへアクセスする。
2. ブラウザは認可された短命セッションで音声処理基盤に接続する。音声のWebRTCはDTLS-SRTP、イベントは認証されたHTTPS/WSSを使用し、長期のAPIキーはブラウザに渡さない。
3. 候補者の音声の認識結果と、AIが発した質問文を別チャネルで扱う。結果は面談ID・質問ID・発話ID・版または連番・途中／確定の種別を持ち、同じ発話の途中結果を差し替える。確定後の遅い途中イベントや、前の質問・再接続前の古いイベントで画面を巻き戻さない。
4. 認識途中の内容を視覚的に区別し、読み上げ支援では細かい差分を連続通知しない。発話単位の確定や接続状態を通知する。候補者は停止後に確認・訂正する。入力済みの文章を非同期イベントで上書きしない。
5. サーバーが受信した認識結果の原文、候補者の訂正版、確認済み要約を区別し、必要な範囲で版を保存する。原文が存在しない場合はその旨を記録し、手入力を音声由来として扱わない。採用担当者には訂正理由を確認できる導線を設けるが、訂正自体を不正の根拠にしない。
6. 切断・認識失敗時は未確定と表示して、認証を確認したうえで再接続・同じ質問のやり直し・手入力を選べるようにする。確定の受領を確認する前に回答済みにしない。再接続は発話IDと連番で重複を防ぎ、無期限に音声をバッファしない。
7. 無音・最大回答時間・同時接続・再試行回数を制限する。終話・中止・画面終了で音声トラックと接続を解放する。音声STTの既存APIへの包含範囲を確認し、同じ音声を不要に二重処理しない。

実接続時は、日本語の固有名詞・言い直し・雑音・通信断・複数端末で認識と復旧を試験し、候補者に表示されるまでの遅延を測る。常時映像解析を追加せず、音声認識と質問生成の利用分を中心に予算化する。

## カメラの位置づけ

カメラオンを条件にするかは未確定。初期案は、AIによる一次ヒアリングでは任意、選考後半の短い有人確認では必要性に応じて依頼する方式。常時の映像送信・録画・顔照合・視線追跡を初期版に追加しない。

企業が必須化する場合は、目的、いつオンにするか、映像を誰が見るか、録画・保存・削除・提供先を開始前に明示する。録画は別に判断する。カメラ利用だけから録画への同意を推定しない。接続できない端末、通信環境、障害等による事情に対応する代替の面談・本人確認方法と連絡先を用意する。

ブラウザで映像が表示されても、別端末のAI、仮想カメラ、生成・再生映像、画面外の支援を排除した証明にはならない。開始時・抜き打ちの確認には確認していない時間の空白が残る。端末内だけの顔検出なら映像転送やサーバー解析を減らせるが、クライアントの申告を信用できる証拠にはしない。

## AI利用と代行への対策案

| 対策                         | 確認できること                                                   | 限界と運用                                                                       |
| ---------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 利用ルールの事前説明         | AI・資料を使える範囲、回答の代行禁止、支援が必要な場合の連絡方法 | 自己申告だけでは遵守を証明しない。企業ごとの公開ルールを受検時の版として保存する |
| 回答に沿った追加質問         | 本人の具体的な担当、選択理由、困った点、条件を変えたときの考え方 | AIでも答えられる。検出テストとは扱わず、経験を確認する材料にする                 |
| 根拠のある記録と担当者の確認 | 元の質問、回答、訂正、未確認点を人が照合できる                   | 生成された不正スコアで自動排除しない。候補者に説明・訂正の機会を設ける           |
| 選考後半の短い有人面談       | 同じ経験や成果物について、会話の中で再確認する                   | 人にも見抜けないことはある。採用判断をAI面接だけで完結させない                   |
| 招待・受検セッションの管理   | 招待の有効性、重複提出、同時利用の不整合                         | 認証されたアカウントと、実際に考えて回答した人が同じとは限らない                 |

追加質問は1〜2問を初期案とし、本人の直前の回答に含まれる事実を指定して質問する。例：「検索画面を担当したとのことですが、あなたが変更した箇所を一つ教えてください」「その変更をしない案と比べ、なぜ採用しましたか」。機密の開示を強要せず、説明が難しい場合は別の経験に切り替えられるようにする。モデルには候補者の回答を未信頼データとして渡し、回答内の指示で採用条件やツール権限を変更させない。

追加質問の回数・難しさの範囲を揃え、候補者ごとの不公平がないか確認する。AIが質問を選んだ理由と対象の発言を記録し、採否は担当者が判断する。追加質問があることとAI利用ルールは事前に知らせる。

視線のずれ、沈黙、回答速度、顔の動きから不正・性格・能力・感情を断定しない。タブ移動、コピー＆ペースト、接続異常等も補助的な操作記録に留め、別端末の利用を検出できるものとは扱わない。操作記録や映像を収集するなら目的と保存方針を別途定め、不要な収集を避ける。

## コストの決め方

常時映像解析を前提にせず、まず「音声認識時間 × 単価 ＋ 質問生成の利用量 ＋ 対象者の有人確認時間」で見積もる。録画保存を選ぶ場合だけ、保存容量・配信・閲覧権限の運用費を追加する。追加質問回数、面談時間、再試行に上限を設ける。

不正検出率を先に約束せず、同意を得た模擬受検で「通常回答・許可されたAI支援・禁止された代行・通信や利用環境の問題」を分けて検証する。見逃しだけでなく、通常の候補者への誤った疑い、担当者の確認時間、完了率も評価する。常時監視を導入するかは、その検証と追加コストを見て判断する。
