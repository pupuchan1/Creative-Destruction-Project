# 同時実行・運用と構成判断 v0.2

すべて本番未検証の設計提案。37件のoffline検証は、分散DB・実ネットワーク・OpenAIサービスの挙動を実証したものではない。

## どの処理にモデルを使うか

| 入力・処理 | 経路 | 理由 |
|---|---|---|
| UIの停止、訂正確定、同意撤回、最終確認 | 認可済み業務APIが直接処理 | 本人の明示操作をモデル分類で妨げない |
| 音声中の操作意図の候補 | 発話をまとめてDecisions、曖昧なら聞き返す | 毎断片への課金・誤分類を抑え、分類だけで確定しない |
| 承認済み質問の単純な次項目 | アプリの計画が決定しLiveへ伝える | 毎回Agentsを呼ぶ必要はない |
| 文脈を踏まえた確認・深掘りの提案 | Agents、アプリが許可した質問・世代を検証 | プロンプトを柔軟にしつつ、質問範囲を固定 |
| 確認済みsnapshotの下書き | Responses strict schema＋根拠参照検証 | 音声の自由発話と保存形式を分離 |

4つのAPIを、すべての発話で必ず直列に呼ぶ設計ではない。Liveが即時の短い応答、backendが必要な場合だけ進行を支える。AIの出力がなくても停止・文字回答・人への相談を使えるようにする。

音声での明確な同意撤回希望は`withdraw`として分ける。検知時は音声入力と新規の生成依頼を一旦止め、UIで撤回/削除の確認を出す。モデル分類だけで不可逆な削除を実行しないが、確認待ちの間も面談を続ける扱いにはしない。UIの撤回操作は即時にサーバーの失効状態へ反映する。

[日本語の意図分類20ケース](../contracts/evaluations/dialogue-intents.json)を用意した。否定、引用、仮定、曖昧な終了、訂正、回答拒否、同意撤回、命令注入、言いよどみ・言い回しの対照例を含む。期待ラベルもレビュー用の提案であり、実モデルに対する評価は未実施。終了/訂正の分類だけで確定しない条件は全ケース共通。誤終了、停止の見逃し、訂正の見逃し、曖昧時の確認率を別々に測り、平均正解率だけで採用を決めない。

## 構成の選択肢

| 案 | 利点 | 条件・コスト | 現在の位置 |
|---|---|---|---|
| Live＋client delegation＋Agents＋必要時Decisions | 既存構想と実装の知見を再利用し、進行をサーバーで制御 | Agents状態の保持・削除管理が必要。音声とbackendを別計測 | 今回の基準案 |
| Live＋stateless Responses中心 | 会話進行の永続状態をアプリへ集約できる | Agentsの機能をアプリで担う。endpointごとのデータ条件は別確認 | ZDR等が必要な顧客で再設計する候補 |
| ASR→テキスト処理→TTS | 部品ごとの挙動と再生成を検査しやすい | 割り込み・同時発話・遅延を自前で組み立てる必要 | 実測でLiveが要件を満たさない場合の比較候補 |

利用できないAPIを検知した際、別方式へ無断でフォールバックしない。記録方法・費用・処理先が変わるため、バージョンを分けて運用条件を確認する。

## DBトランザクションと多重実行

業務更新は、主体と企業の確認→対象面談の行ロック→失効確認→冪等操作の取得→revision照合→更新→outbox登録を一つのトランザクションで行う。キャッシュ応答でも失効確認を省略しない。`(tenant_id, subject_id, method, route, idempotency_key_hash)`を一意にし、payload hashが異なる再利用は409。

Liveの同時作成には面談ごとのactive connection予約を一つだけ持つ。予約はprovider呼出前に保存し、operation_id、作成中/成功/不明、provider ID、開始時刻を持つ。タイムアウトで結果が不明なら予約を外して即時再作成しない。既存接続の照合または期限処理で解決し、候補者には文字回答/再試行待ちを示す。

Node所有権にはleaseと単調増加するfencing tokenを用いる。初期提案は15秒lease・5秒renew。古いownerのイベント・ツール結果はfencing tokenとgenerationの両方で拒否する。lease失効はデータの消去ではなく、接続を停止して復旧へ移る条件。workerが落ちても同じジョブのside effectを二重実行しない。

訂正時は正規発話のrevision、transcript_version、generation、旧reportのstale化、outboxを同時に更新する。レポート保存と人のreviewも、作成時のtranscript_versionが現在と一致する条件付き更新にする。cancelの到着だけを信用せず、遅い完了結果にも同じ条件を適用する。

## SSEと遅いブラウザー

snapshotとlast_seqは同じDB snapshotから読む。イベントを先に削除してからsnapshotを返すと再接続時に欠落するため、保存期間とページングを揃える。snapshot取得後に起きた更新は、last_seqからの永続再生で回収する。

認可は接続時だけでなく担当変更・セッション失効時にも適用する。失効イベントで既存streamを閉じ、再接続は最新権限で検証する。候補者の字幕に担当者の内部reviewメモを含めない。遅いクライアントに無制限のメモリバッファを確保せず、切断とcursor再生へ切り替える。cursorの範囲外は422、保持期限外は410。候補者データはCDN・service workerでキャッシュしない。

## 課金と運用指標

Liveのusage.secondsは累計であり、10→20→30秒のイベントを60秒として加算しない。接続ごとの最新値を保持し、再接続の別IDだけ合算する。closed前の切断は既知の使用量を残して「最終化未確認」とする。再接続が重複課金を増やすことも面談単位で見えるようにする。

試算コードは[contract_lab/costs.py](../contract_lab/costs.py)。2026-10-22確認単価のStandard/非cached/追加料金なしという限定条件で、前回の30分$1.668の例を再計算する。入力する秒数はプロバイダーの観測usageであり、初期課金や最小時間を勝手に推定・二重加算しない。請求書照合の代わりにはならない。

| 指標 | 定義・見る理由 |
|---|---|
| 音声初動遅延 | 候補者の発話終端→最初の可聴出力。文字断片の受信間隔で代用しない |
| 次質問遅延 | 発話終端→有効なgenerationの次質問の可聴出力。即時の相づちと区別 |
| 訂正反映時間 | 訂正確認のPOST→正本更新と旧生成物の失効通知 |
| 欠落率 | provider最終化未確認の接続数/全接続数。再接続でリセットしない |
| 完了率 | 同意済み面談に対する本人確認済み記録。取消・回線失敗を別理由で集計 |
| 面談原価 | Live秒、全モデル入力/出力、Decisions回数、再試行、DB/転送、人の確認工数 |
| 削除滞留 | 期限超過のlive data/provider state削除件数。backup期限と区別 |

同時接続・時間・tokenの上限はテナント別に予約し、成功後だけ加算する仕組みにしない。上限到達時は保存済み回答を保持して停止/人への切替を案内する。候補者の評価を下げない。初期の遅延目標は測定目標でありSLAとして販売しない。

## 障害と削除の運用

| 事象 | 保存する情報 | 復旧方針 |
|---|---|---|
| 429/一時的5xx | request ID、operation ID、世代、試行数、本文なしのエラー | 最大回数を守ってbackoff。新しい接続を無限作成しない |
| Node再起動・sideband断 | 最後のseq、connection、原断片の保存位置、gap | 戻せない文字記録を補完せず欠落を表示し、人へ確認 |
| レポートschema/根拠不一致 | reason code、prompt/model版、job ID | 保存・reviewへ進めない。上限後は手動対応 |
| 同意撤回 | 失効時刻、generation、停止の確認状態 | まず拒否状態にし、停止未確認を完了と表示しない |
| 削除の一部失敗 | app/provider/backupの個別進捗 | queued/running/blockedを表示。本文のあるSSE・cache・audit・jobも対象 |

削除statusのcompletedは、稼働中データとproviderアプリ状態の削除確認、backupへの削除tombstone適用を条件とする。backupの物理失効日はbackup_expiry_atで別に示す。上流のabuse monitoringや法的に保持すべき最小記録まで即時消去したと表示しない。バックアップ復元時はtombstoneを再適用してから接続を再開する。この運用は未実装・未検証。

実候補者の導入前に、担当責任者、顧客の採用段階、利用説明、保持期間、処理地域、質問の承認、削除の実動作、障害窓口を確定する。それまでは架空データと既存画面の接続検証を進められる。
